---
title: Environments
description: One Chaski Worker per environment of your app, each with resources of its own, from one project.
---

Each environment of your app, such as production and staging, gets a Chaski Worker of its own,
with its own database, queue, dashboard and channel settings. One Chaski project deploys them all:
the top of its `wrangler.jsonc` is production, as [Install](/docs/install) sets it up, and every
other environment is a block under `env`.

## Add an environment

Create its resources, under names of its own:

```bash
npx wrangler d1 create chaski-staging
npx wrangler queues create chaski-staging-deliveries
npx wrangler queues create chaski-staging-deliveries-dlq
```

Then declare them in an `env` block. Wrangler doesn’t carry bindings or vars from the top of the
file into an environment, so the block repeats each one, with that environment’s names:

```jsonc title="wrangler.jsonc"
{
  "name": "chaski",
  // …production, as Install sets it up
  "env": {
    "staging": {
      "vars": {
        "CHASKI_ENVIRONMENT": "staging",
        "CHASKI_PUBLIC_URL": "https://staging.example.com/me/notifications"
      },
      "d1_databases": [
        {
          "binding": "CHASKI_DB",
          "database_name": "chaski-staging",
          "database_id": "<id printed by wrangler d1 create>",
          "migrations_dir": "node_modules/chaskijs/migrations"
        }
      ],
      "queues": {
        "producers": [{ "binding": "CHASKI_QUEUE", "queue": "chaski-staging-deliveries" }],
        "consumers": [
          {
            "queue": "chaski-staging-deliveries",
            "max_batch_size": 10,
            "max_batch_timeout": 1,
            "max_retries": 5,
            "dead_letter_queue": "chaski-staging-deliveries-dlq"
          }
        ]
      },
      "durable_objects": {
        "bindings": [
          { "name": "CHASKI_FEED", "class_name": "ChaskiFeed" },
          { "name": "CHASKI_EVENTS", "class_name": "ChaskiEvents" }
        ]
      },
      "workflows": [
        {
          "name": "chaski-staging-scheduler",
          "binding": "CHASKI_SCHEDULER",
          "class_name": "ChaskiScheduler"
        }
      ],
      "send_email": [{ "name": "CHASKI_EMAIL" }]
    }
  }
}
```

The Workflow needs a name of its own in every environment, since its name is unique in your
account. Wrangler names the Worker `chaski-staging`, after the top-level `name` and the
environment.

## Deploy it

Every Wrangler command takes the environment with `--env`, the secret included:

```bash
openssl rand -base64 32 | npx wrangler secret put CHASKI_SECRET --env staging
npx wrangler d1 migrations apply CHASKI_DB --remote --env staging
npx wrangler deploy --env staging
```

Then turn on Cloudflare Access for its URL and set up its channels in its own dashboard, as
[Install](/docs/install#turn-on-cloudflare-access) does for production. Settings never move
between environments: staging can send from a test domain while production sends from your own.

## Bind each app environment to its Chaski

Your app’s `staging` environment binds to `chaski-staging`, and its production to `chaski`:

```jsonc title="wrangler.jsonc (your app)"
{
  "services": [{ "binding": "CHASKI", "service": "chaski", "entrypoint": "ChaskiEntrypoint" }],
  "env": {
    "staging": {
      "services": [
        { "binding": "CHASKI", "service": "chaski-staging", "entrypoint": "ChaskiEntrypoint" }
      ]
    }
  }
}
```

The code doesn’t change: it calls `env.CHASKI` in every environment, and each one reaches its own
Chaski.

## Keep them in step

An upgrade goes to every environment the same way: update `chaskijs`, then apply the migrations
and deploy, environment by environment, staging first. The dashboard’s header names the
environment from `CHASKI_ENVIRONMENT`, so nobody mistakes one for the other.
